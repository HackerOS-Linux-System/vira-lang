= Hyper Lang

Statycznie typowany język transpilowany do JavaScript, z natywną obsługą
bibliotek npm/JSR/TS bez pisania ani utrzymywania osobnych wrapperów czy
plików `.d.ts`.

Dokumentacja: link:website/home.html[strona główna] &middot;
link:website/docs.html[referencja języka] &middot;
link:website/vira.html[referencja vira]

== Szybki start

[source,bash]
----
go build -o hyperc ./src/hyperc
./hyperc examples/hello.hyper -o hello.js
node hello.js
----

Na co dzień: `vira new`, `vira install`, `vira build`, `vira run` - patrz
link:website/vira.html[dokumentacja vira].

== Filozofia narzędzi (jak w Go)

`hyperc` robi **wyłącznie kompilację** - `hyperc plik.hyper [-o wyjście] [--check] [--json]`,
nic więcej. Formatowanie (`hyperfmt`) i LSP (`hyperls`) to **osobne binarki**,
dokładnie jak `gofmt`/`gopls` są osobne od `go`. `vira` orkiestruje
wszystko na poziomie projektu (`vira build`, `vira run`, `vira fmt`,
`vira lsp`, `vira check`, `vira publish`, `vira install/remove/search`) -
tam żyje codzienny workflow, nie w samym kompilatorze.

== Co jest zaimplementowane (v0.3)

=== Kompilator

* lekser, parser, statyczny checker, generator JS, moduły między plikami
* **walidacja, że zaimportowana nazwa lokalna FAKTYCZNIE istnieje w module źródłowym** - literówka w imporcie jest dziś błędem kompilatora, nie `ReferenceError` w node (złapało to nawet literówki we własnych testach napisanych w tej sesji)
* diagnostyki ze ścieżką pliku źródłowego, inferencja typu przez łańcuchy wywołań, egzekwowanie `pub`, zgodność traitów, wyczerpujący `match`, `throw`/`try`/`catch`/`finally`, literał obiektu, destrukturyzacja, spread, ternary, aliasy importów, generyki jako JSDoc, precyzyjne grupowanie wyrażeń w JS

=== Narzędzia

* `hyperc` - wyłącznie kompilacja
* `hyperfmt` - re-indenter
* `hyperls` - LSP: diagnostyka na żywo, formatowanie, **oraz teraz hover i go-to-definition** dla deklaracji top-level (funkcje/struktury/enumy/traity), oparte o `checker.Index` + retokenizację dokumentu w miejscu kursora - **przetestowane jako prawdziwy klient JSON-RPC**

=== vira (13 plików `.hyper`)

* `vira new/install/remove/search/check/fmt/build/run/lsp/publish`
* **resolver semver** (`^`, `~`, dokładna wersja, `*`) - własna implementacja w `semver.hyper`, przetestowana na 10 przypadkach
* **realne pobieranie i rozpakowywanie paczek** do `.vira/packages/<nazwa>@<wersja>/` - tarball przez `tar` dla npm/JSR, płytki `git clone` dla vira.io - **przetestowane realnie** (prawdziwe pliki `left-pad`/`is-odd` na dysku po `vira install`)
* **scaffolding Tauri** (`vira build --release --target tauri`) - generuje Cargo.toml/tauri.conf.json/main.rs jeśli `src-tauri/` nie istnieje - pliki wygenerowane i zweryfikowane, samo `cargo tauri build` niesprawdzone (brak toolchainu Rust w środowisku)
* trzy rejestry: npm, JSR (`jsr:`, nieprzetestowane realnie - brak dostępu do `jsr.io` w tej piaskownicy), vira.io (`vira:`, **przetestowane realnym zapytaniem** do `raw.githubusercontent.com/vira-io/repository`)
* `vira build --release` (bez `--target`) buduje samodzielną binarkę Node SEA - przetestowane, plik ELF ~120MB uruchamialny bez node w PATH

=== cmd/ - bootstrap (dwa kanarki)

* `cmd/src/lexer.hyper` - działający lekser
* `cmd/src/parser.hyper` - **nowy**: parser wyrażeń arytmetycznych (recursive descent + precedence climbing) napisany w Hyper Lang, przetestowany m.in. na dokładnie tym przypadku (`2 + 3 * 4` vs `(2 + 3) * 4`), który złapał realny bug w samym `hyperc`
* `cmd/std/` - 82 moduły + **2 nowe z prawdziwą logiką** (nie wrapperami): `string/slugify.hyper` (normalizacja do url-slug) i `collections/linkedlist.hyper` (lista wiązana z węzłami) + **test suite** (`std_test.hyper`, 26 asercji, wszystkie przechodzą) - który po drodze złapał dwie literówki we własnych importach dzięki nowej walidacji importów

=== website/

* wyszukiwarka po stronie klienta (vanilla JS, bez zależności) w `docs.html`/`vira.html`
* tabele stanu implementacji zaktualizowane

== Co pozostaje zablokowane (nie moje ograniczenia kodu, tylko środowiska)

* **JSR na żywo** - `jsr.io`/`npm.jsr.io`/`api.jsr.io` nie są dostępne z tej piaskownicy (biała lista domen sieciowych). Kod istnieje i jest analogiczny do już sprawdzonego npm, ale niezweryfikowany.
* **`.eopkg`/OpenBSD `pkg_add` jako natywne pakiety** - wymagają odpowiednio `solbuild` i `pkg_create`, których GitHub Actions nie udostępnia jako hostowanych runnerów. Joby w CI są gotowe i wyłączone (`if: false`), czekają na self-hosted runner - to decyzja infrastrukturalna, nie coś do naprawienia kodem.
* **Pełny self-hosted parser/checker/codegen** - dwa kanarki (lekser, parser wyrażeń) działają i są przetestowane. Parser CAŁEGO języka to już wielotygodniowy projekt, nie coś do dorzucenia w tej samej sesji - patrz `cmd/README.adoc` po uzasadnienie kolejności kroków.

== Co nadal wymaga rozbudowy

* Pełna unifikacja typów (dziś: proste przypisania + łańcuchy wywołań)
* Generyki z ograniczeniami (`T: Trait`) - parsowane, nieegzekwowane
* Sourcemapy
* LSP: completion ze świadomością zasięgów lokalnych
* Formatter jako pełny pretty-printer (wymaga trivia dla komentarzy w parserze)
* Rozwiązywanie CAŁEGO drzewa zależności przechodnich w `vira install` (dziś: płaska struktura, bez zagnieżdżonych zależności zależności)
* Cross-kompilacja w `vira build --release`
* Bootstrap `cmd/`: lekser v0.3, parser instrukcji/deklaracji v0.3,
  podstawowy checker, codegen i bundler (kanarki 1-6, ze spiętym
  pipeline'em bundle -> check -> codegen) gotowe - ale bez integracji
  z prawdziwym `std/fs` (bundler działa na danych z pamięci), bez
  inferencji typów (checker sprawdza tylko istnienie nazw) i bez
  sprawdzania wyczerpywalności `match` (patrz `cmd/README.adoc`)
* Hashmapa/słownik w bibliotece standardowej (dziś: `stack`, `linkedlist`,
  `queue` w `cmd/std/collections/`, zero NATYWNEGO słownika - `checker.hyper`
  obchodzi to interopem z JS `Map`, co się sprawdziło, ale natywny typ
  wciąż byłby czytelniejszy niż pamiętanie, które zmienne to `Map`)
